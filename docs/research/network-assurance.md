# 如何判断一条 rutis 链路安全、稳定、可信

[English](network-assurance.en.md) · [组网与服务边界](network-groups.md) · [网络栈](network-stacks.md) · [通信协议](communication-protocols.md)

设备经网关上报温度。网关的证书有效，云端收到了消息，屏幕也显示“在线”。这些观察留下了三个问题。谁有权发布这台设备的读数？网关断线十分钟后能补回哪些样本？屏幕上的值是刚测到的，还是昨天的保留消息？

| 观察维度 | 需要回答的问题 | 谁掌握证据 |
| --- | --- | --- |
| 安全 | 谁可以连接、读取、发布或执行操作？机密性与完整性保护到哪一跳？ | 链接行验证对端，网关或 broker 执行边界策略，应用检查具体方法和资源权限。 |
| 稳定 | 慢、断、满或切换路径时，哪些功能仍可用？损失多大、多久恢复？ | 传输两端观测路径和会话，队列报告积压与过期，业务方观测服务何时重新产生有效结果。 |
| 可信 | 谁对哪个事实作证，证据经过哪些中间方，何时失效？ | 设备或网关声明来源，验证方检查身份、完整性与新鲜度，业务方确认执行结果。 |

以下以 rutis 0.23.0 为基线。第 1 节记录现状，其余各节给出评估方法和建议的验收实验。

## 1. 当前实现能证明什么

- **gRPC 链接准入。** 在配置 mTLS 的服务器上，Go 端点检查已验证的客户端证书链及配置的证书名称，再接纳隧道。客户端每次重连重新读取 CA、证书和私钥。运行中的隧道不会因磁盘文件更换而自动重新认证。部署方若要求撤权即时影响现有连接，还要有明确的终止机制。[云端准入](../../link/grpc/endpoint.go) · [设备重连](../../link/grpc/client.go)
- **会话的信任范围。** rutis 从 Hello 读取对端自报 ID，以它命名远端插件。链路凭据留在各自的适配器。原生节点会话信任已接入的节点，可共享服务和事件，并可请求运行本地加载器能解析的插件。若两个独立管理的域只约定一个业务接口，可由应用网关终止请求、显式导出该接口并逐次授权。[rutis 节点安全模型](https://github.com/arcships/rutis/blob/v0.23.0/docs/guide/nodes.md#安全) · [链接插件契约](../design/01-link-plugin-contract.md)
- **恢复与资源上限。** Go gRPC 客户端已有退避、鉴权拒绝后的较长等待，以及云端停机时的隧道清理。它限制单帧大小。rutis 0.23 的非 Rust `sessions.open` 接口没有设置整个会话出站队列上限的参数。帧大小测试与队列积压测试回答不同的问题。[gRPC 收发](../../link/grpc/session.go) · [现有回归测试](../../link/grpc/reconnect_test.go) · [契约中的队列限制](../design/01-link-plugin-contract.md)

## 2. 安全沿路径逐跳判断

以“设备 → broker → 站点网关 → 云应用”为例，先标出哪里终止 TLS、哪里能读写明文、哪里作出准入或业务授权决定。透明 relay 可以只转发端到端保护的数据，终止协议的网关则成为新的信任方。对每一段检查四件事。

1. **身份和权限。** 由部署方指定信任根、期望的对端身份、允许的方向和范围。发现记录、设备标签和服务名可以帮助找到候选。建连时仍需验证对端，发布到主题或调用业务方法时仍需相应授权。同一域内两台合法设备也可能拥有不同权限。[TLS 服务身份](https://datatracker.ietf.org/doc/html/rfc9525)
2. **数据保护。** 对两个分别终止在 broker 的 TLS 连接，云端能验证它所连的 broker。若应用要求“这条记录确实来自设备 A，转发方无法改写”，可以使用设备生成的对象级完整性证据，覆盖来源、数据、序号和必要上下文，并管理验证密钥。OSCORE 展示了受限设备在兼容的 CoAP 代理路径上保护对象的做法。[TLS](https://datatracker.ietf.org/doc/html/rfc8446) · [OSCORE](https://datatracker.ietf.org/doc/html/rfc8613)
3. **轮换、撤权和分区。** 明确谁发行、轮换或撤销凭据，已有会话何时结束，目录记录与离线队列多久过期。对于敏感操作，验证方在失联时是拒绝、等待，还是接受有限期的缓存授权，应由策略所有者决定。队列恢复后按操作契约检查权限和期限，尤其要覆盖撤权前入队、撤权后才送达的请求。
4. **插件与配置。** 能读取设备密钥或修改导出规则的本地插件本身就是信任方。部署者验证插件包来源与版本、限制行可访问的凭据，并保留可回滚的策略版本。诊断记录身份引用、错误类别和策略版本，避免记录令牌、私钥和完整业务载荷。[行级凭据与管理职责](../design/01-link-plugin-contract.md)

## 3. 稳定性用故障结果衡量

| 故障 | 基础设施可采取的动作 | 验收时观察 |
| --- | --- | --- |
| 大批设备同时断线 | 每次尝试设期限、限制并发拨号，按错误类别退避。评估带抖动的重试与总重试预算，明确哪一层重试。 | 每秒尝试次数、达到可用服务的恢复时间分布、授权服务或 broker 的峰值负载。[重试与抖动](https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/) |
| 慢消费者或下游停顿 | 限制在途数、队列字节数与滞留时间。按契约阻塞、拒绝、合并状态或落盘。命令、状态快照和审计事件可有不同策略。 | 高水位、最旧消息年龄、过期与丢弃数，以及其他租户的请求是否仍能完成。[过载与级联故障](https://sre.google/sre-book/addressing-cascading-failures/) |
| 直连变差、切换到 relay | 验证备用路径并限制来回切换。新会话有独立生命周期，在途调用可能结果未知。 | 分别记录路径恢复、会话恢复、第一次业务成功的时间。核对相同请求 ID 实际执行次数。 |
| 域间分区或部分节点不可达 | 标记观察来源与有效期，区分最后所见、未知和主动撤回。群体调用返回逐成员状态，应用决定是否接受部分结果。 | 目录可用但业务不可达、只有部分成员应答、重连后旧记录或过期命令到达等情况。 |
| 云服务重启或升级 | 停止接新会话，在期限内排空或终止活动会话。新实例明确哪些状态持久化，哪些需要对端重建。 | 空闲隧道、阻塞发送和未完成请求能否结束，重启后的会话与订阅能否恢复。[gRPC 插件指南](../guide/link-plugins.md) |

每个部署可选自己的指标和目标。例如，把“有效期内完成采样并返回结果的请求数 / 已接纳采样请求数”作为业务成功率，同时记录准入拒绝和过载拒绝数，避免服务通过拒收请求显得更稳定。按观测点拆开路径、会话与业务指标，门槛由部署方按电池、带宽、任务时限和允许损失设定。

## 4. 可信需要可追溯的证据

一次温度查询可呈现四条有明确来源的事实。链接行在某时接入了指定网关。broker 确认收到一条发布。采集插件收到设备标注为 10:01 的样本。设备应用对请求 ID 返回“采样完成”。每条记录都写明声明者、对象、观察位置、时间和有效范围。对外展示时允许“未知”“过期”“仅网关声明”等结果。[MQTT 确认与恢复](communication-protocols.md)

- **来源与新鲜度。** 分开保存设备采样时间、接收时间、序号或启动代次，以及数据经过的网关。时钟误差未知时要显式标记。签名验证可以确认签名者及其声明的内容，但校准、安装位置或物理测量准确度仍需设备或业务侧证据。
- **交付与执行。** 为一次业务操作使用稳定请求 ID。用它关联入队、转发、设备回复和业务提交。发现确认丢失时，允许查询执行结果或按业务规则幂等重试。交付保证的作用范围止于作出该确认的一方。[通信协议研究](communication-protocols.md)
- **证明强度取决于用途。** 显示最近读数时，可信网关来源和样本年龄可能足够。若应用还依赖特定设备软件状态，可让验证方按策略评估远程证明，并检查证明结果的新鲜度。远程证明只支持其覆盖的声明。是否准许某项操作仍由依赖方决定。[IETF RATS 架构](https://datatracker.ietf.org/doc/html/rfc9334)

## 5. 三个可重复的验收场景

| 场景 | 建议的本地实验 | 预期可区分的结果 |
| --- | --- | --- |
| IoT 设备经 MQTT 上报 | 发布带设备 ID、采样时间和序号的 retained 温度后让设备离线。采集插件重新订阅，在测试 broker 上撤销设备发布权，再让设备用原凭据重连并尝试发布。另用仍在线的测试会话检查策略何时生效。 | 旧样本带上原采样时间，页面能显示过期。分别核对 broker 是否接受新发布、现有会话如何处置、已入队的数据如何标记。 |
| 两个自治域经网关访问服务 | 两个域内各有同名设备。只向合作域导出其中一台的读取接口。对照获准读取、权限不符的写入，以及跨域链路断开后三种结果。 | 审计能定位来源域、接口、决策者与策略版本。可见的服务名不会扩大操作权限，路径失联时目录显示最后观测及年龄。 |
| 双路径上的在途任务 | 在测试应用提交任务后、回执返回前断开直连，通过 relay 建立新会话。先查询原请求 ID，再按业务契约决定是否重试。 | 网络报告路径与会话恢复。应用能说明任务已完成、待执行或结果未知，并给出实际执行次数。 |

这些场景是研究中提出的验收条件。可直接复用的既有证据包括仓库中的 gRPC 准入、证书重连、排空和双宿主测试。跨协议撤权、来源证明和跨域审计需要各集成方按实际部署验证。[gRPC 测试](../../link/grpc/session_test.go) · [双宿主测试](../../link/grpc/hosts_test.go)
