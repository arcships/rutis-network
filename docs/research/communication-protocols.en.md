# Communication protocols for delivery, acknowledgment and recovery

[中文](communication-protocols.md) · [Network stack survey](network-stacks.en.md) · [Network groups and service boundaries](network-groups.en.md)

A Wi-Fi device connected to an MQTT broker can publish temperature readings, receive notices and subscribe to commands. Its network stack determines broker reachability. Its communication protocol determines who receives each message, who acknowledges it and where messages go while a device is offline. These guarantees determine what a rutis plugin can report to its caller.

**Four questions guide protocol selection.** Is the recipient a named peer, every subscriber, one competing worker or a device that will return later? Does the sender observe protocol acceptance, durable storage, consumer acknowledgment or a business outcome? Which connection, session, queue, partition or subscription bounds ordering and acknowledgment? Where does recovery start after disconnect, and what might be duplicated?

Suppose a collector goes offline at 10:00 while a sensor publishes a reading each minute from 10:01 to 10:03. An ordinary Core NATS subscriber returning at 10:04 receives subsequent live publications. With a qualifying MQTT subscription established before disconnect, the broker can deliver pending matching QoS 1/2 messages while the session and messages remain valid. If only a retained temperature exists, a new subscription normally gets the last retained value. A Kafka consumer can resume at the committed position for each partition while the records remain in the log. These are different uses of online notification, offline subscription state and replayable history. [Core NATS](https://docs.nats.io/nats-concepts/core-nats) · [MQTT 5](https://docs.oasis-open.org/mqtt/mqtt/v5.0/os/mqtt-v5.0-os.html) · [Kafka design](https://kafka.apache.org/41/design/design/)

The tables compare device data, queues and logs, and live and federated communication. They include open wire protocols and operationally distinct service APIs such as SQS. Kafka and Redis entries identify the specific messaging model. CloudEvents describes an event envelope, Protobuf and JSON represent data, and AsyncAPI describes an interface contract. Delivery and recovery depend on the chosen protocol. [CloudEvents](https://cloudevents.io/) · [AsyncAPI](https://www.asyncapi.com/docs/reference/specification/latest)

## 2. Routing, work queues and replayable logs

| Protocol or service | Address and distribution | Acknowledgment and recovery |
| --- | --- | --- |
| AMQP 0-9-1 / RabbitMQ | Publish to an exchange. Bindings route messages to queues, where consumers can compete for work. | Publisher confirms and consumer ACKs are independent. Handle unroutable messages when queue routing is required. Queue durability, message persistence and redelivery settings each matter. [AMQP 0-9-1](https://www.rabbitmq.com/amqp-0-9-1-protocol) · [RabbitMQ confirms](https://www.rabbitmq.com/docs/confirms) |
| AMQP 1.0 | Links connect sources to targets, transfers carry messages and credit controls flow. Version 1.0 has a distinct wire protocol from 0-9-1. | Inspect delivery outcomes and settlement for acceptance, rejection or release. Persistence and recovery depend on the endpoint and configuration. [AMQP transport](https://docs.oasis-open.org/amqp/core/v1.0/os/amqp-core-transport-v1.0-os.html) |
| STOMP 1.2 | Clients send or subscribe to a destination whose meaning is server-specific. | Select auto, client or client-individual acknowledgment. A RECEIPT concerns the server processing a client frame. Check broker policy for queue retention and replay. [STOMP 1.2](https://stomp.github.io/stomp-specification-1.2.html) |
| Core NATS | Ordinary subject subscriptions fan out. A queue group selects one available member. A reply subject enables request/reply. | Core NATS provides at-most-once delivery. It does not accumulate a disconnected subscriber's missed messages. [Core NATS](https://docs.nats.io/nats-concepts/core-nats) |
| NATS JetStream | Streams capture messages by subject. Consumers track delivery state, with configurable durability, start positions and explicit acknowledgment. | Separate the publish acknowledgment from consumer acknowledgment. Retention, AckWait and redelivery policy determine recovery and duplicate windows. [JetStream](https://docs.nats.io/nats-concepts/jetstream) · [Consumers](https://docs.nats.io/nats-concepts/jetstream/consumers) |
| Redis Pub/Sub · Redis Streams | Pub/Sub pushes to matching live subscribers. Streams store entries under a key, readable by ID or through a consumer group. | Disconnected Pub/Sub subscribers miss messages. XACK clears a group's pending entry. Stream trimming and Redis persistence are independent settings. [Redis Pub/Sub](https://redis.io/docs/latest/develop/pubsub/) · [Redis Streams](https://redis.io/docs/latest/develop/data-types/streams/) |
| Apache Kafka | Topics are partitioned logs with ordering within each partition. Conventional consumer groups coordinate partition consumption. Independent groups can read the same records. | Committed offsets track progress. Consumers can rewind within retention. Kafka transactions have a defined scope for Kafka reads and writes. External effects require coordination with the consumed position. [Kafka design](https://kafka.apache.org/41/design/design/) |
| Apache Pulsar | Topics can have several named subscriptions. Exclusive, Failover, Shared and Key_Shared change dispatch within one subscription. | Acknowledgment and redelivery are scoped to a subscription. Backlog, retention of acknowledged messages and subscription type determine replay and possible reordering. [Pulsar messaging](https://pulsar.apache.org/docs/4.0.x/concepts-messaging/) |
| Apache RocketMQ | Producers publish to topics and consumers coordinate through groups. A delayed message can become available at its scheduled time. | Consumption mode and group policy govern retries and dead lettering. Keep an application identity to handle redelivery after an ambiguous timeout. [RocketMQ retries](https://rocketmq.apache.org/docs/featureBehavior/10consumerretrypolicy/) · [Delay messages](https://rocketmq.apache.org/docs/featureBehavior/02delaymessage/) |
| Managed queue API · Amazon SQS Standard | Clients receive messages through the service API. A received item becomes temporarily invisible to other consumers. | Delete after processing using the receipt handle. Visibility timeout can cause redelivery. ## 4. Integrating MQTT with rutis

Consider a temperature sensor publishing its latest reading to `plant/a/sensors/t1/state`. It accepts “sample now” on `plant/a/sensors/t1/requests` and sends a result carrying the request ID on another topic. Two historical readings, the last known value and confirmation of a new sample are distinct data.

| MQTT mechanism | Plugin interpretation |
| --- | --- |
| QoS 0 / 1 / 2 | At most once, at least once and exactly once apply to the protocol exchange on each leg from publisher to broker and broker to subscriber. Granted subscription QoS also bounds downstream delivery. Tolerate duplicates at QoS 1. QoS 2 cannot atomically commit a sample on the device and a write in the application's database. |
| Retained publication, session recovery and expiry | Retain stores the latest retained value per exact topic. MQTT 3.1.1 can resume a session with a stable Client ID and Clean Session=false. MQTT 5 separates Clean Start from Session Expiry and supports Message Expiry. Inspect Session Present in CONNACK before deciding to rebuild subscriptions. Carry a measurement timestamp to identify old readings after reconnect. |
| Ordinary and shared subscriptions, and Will | Ordinary independent subscriptions can deliver one copy to each monitor. A shared subscription can distribute work among workers. A Will is a connection-related notification triggered by the broker under protocol rules, potentially subject to Will Delay. Actual equipment condition requires separate evidence. |
| Requests and results | MQTT 5 provides Response Topic and Correlation Data. Subscribe to the response topic first, set a deadline and correlate by request ID. On 3.1.1, peers can agree on a response topic and payload. A publish acknowledgment covers publication. The device sends a separate result after sampling. |
| Redelivery and authorization | Use a non-retained publication with an application request ID and expiry for a one-shot command. Deduplicate by request ID at the device. MQTT Packet Identifiers can be reused and are scoped to protocol exchanges. The operator grants topic access. Caller-specific business authorization needs trusted identity information. An ordinary delivered publication does not automatically carry the publisher's authenticated identity. |

These interpretations follow the protocol rules for QoS, sessions, retained publications and request/response. [MQTT 5](https://docs.oasis-open.org/mqtt/mqtt/v5.0/os/mqtt-v5.0-os.html) · [MQTT 3.1.1](https://docs.oasis-open.org/mqtt/mqtt/v3.1.1/os/mqtt-v3.1.1-os.html)

**Go plugin responsibilities.** A configuration row could hold the broker address, credential reference, Client ID, allowed topic filters and session policy. Its runtime connects and subscribes, limits in-flight work, stops reconnects on unload, frees local resources and applies the configured broker-session policy. Preserve topic, delivered QoS, retain flag and available correlation fields. Keep the sample timestamp when the payload supplies one and record receipt time separately. Application plugins inject the publisher service or subscribe to events to handle sampling, storage or alarms. A bidirectional bridge should limit inbound and outbound topic mappings, record provenance and check for feedback loops. Eclipse Paho provides distinct Go clients for MQTT 3.x and MQTT 5. This is a proposed integration. [Paho MQTT 3.x](https://github.com/eclipse-paho/paho.mqtt.golang) · [Paho MQTT 5](https://github.com/eclipse-paho/paho.golang)

Ordinary topics naturally expose publish and subscribe. To carry a peer session between two rutis plugins through a broker, both endpoints would also need agreed pairing and admission, message boundaries and ordering in each direction, duplicate handling, bounded backpressure, disconnect propagation and isolation from an earlier connection's messages. A channel meeting that contract can be passed to `rutis/sessions.open(far)`. [Link plugin contract](../design/01-link-plugin-contract.en.md)

## 5. Acceptance scenarios with observable failures

For withdrawal of publish permissions, retained sample freshness and gateway provenance, see [security, reliability and trustworthiness](network-assurance.en.md).

These are proposed checks. Capture evidence independently at the publisher, broker, subscriber and application.

1. **Offline subscriber.** Establish a QoS 1 subscription with a stable Client ID, disconnect, publish three numbered messages that remain valid, and reconnect before session expiry. Check session resumption and the actual numbers received. Contrast a fresh session with non-retained publications.
2. **Late joiner.** Publish three retained state updates. A new ordinary subscriber should receive the latest retained value. Subscribing again to the command topic should not trigger historical sampling requests.
3. **Lost acknowledgment after a business effect.** Disconnect after writing the sample but before delivering a consumer acknowledgment or application reply. Allow a timeout or redelivery, then query the result with the original request ID. Check executions and replies separately.
4. **Fan-out and work sharing.** Send uniquely identified events to two ordinary subscribers and a shared subscription with two members. For a single delivery without faults, both ordinary subscribers should receive a copy and one group member should receive the shared delivery. Disconnect a group member and record redelivery separately.

## 6. Raw UDP and lightweight datagram protocols

Here raw UDP means application-defined datagrams sent and received through an ordinary UDP socket. The OS handles IP and UDP headers. Each datagram preserves one message boundary. A successful send means the local stack accepted it. UDP supplies no connection handshake, delivery acknowledgment, ordering, duplicate suppression, peer-close notification or sender authentication. Unicast targets an address and port. IPv4 broadcast and IP multicast can reach multiple receivers. Joining a multicast group does not supply an authoritative roster of online application peers. [UDP](https://datatracker.ietf.org/doc/html/rfc768) · [UDP usage guidelines](https://datatracker.ietf.org/doc/html/rfc8085) · [IP multicast](https://datatracker.ietf.org/doc/html/rfc1112)

| Protocol or use | What it adds over UDP | What a rutis plugin can report |
| --- | --- | --- |
| Custom telemetry, heartbeats and LAN announcements | A minimal datagram can carry a single sample. A device protocol with a boot generation, sequence number and sample timestamp lets receivers identify duplicates, late arrivals and sequence gaps. | Report the received sample, source and last-seen time. A gap can reflect network loss, a local drop or a skipped sequence number at the sender. |
| DNS / mDNS | DNS correlates queries and responses and can use TCP when needed. mDNS supports link-local multicast queries and cached records with TTLs. | Expose candidate names, addresses, interfaces and expiry. A resolved record still needs a separate service and peer identity check. [DNS](https://datatracker.ietf.org/doc/html/rfc1035) · [mDNS](https://datatracker.ietf.org/doc/html/rfc6762) |
| DHCPv4 / NTP | DHCPv4 negotiates address leases over several messages. An NTP client uses timestamps in a request/reply exchange to estimate clock offset and round-trip delay. | One describes network configuration and validity, the other a clock observation with uncertainty. A reply from either service says little about the device application. [DHCPv4](https://datatracker.ietf.org/doc/html/rfc2131) · [NTP](https://datatracker.ietf.org/doc/html/rfc5905) |
| Syslog over UDP / SNMP Trap and Inform | UDP Syslog and traps send one-way notifications. A matching response to an SNMP inform is defined, and the originator may retry on timeout. | Distinguish a local send, receipt at the collector and a response from a remote SNMP engine. A person or application handling the alert needs its own acknowledgment. [UDP Syslog](https://datatracker.ietf.org/doc/html/rfc5426) · [SNMP operations](https://datatracker.ietf.org/doc/html/rfc3416) |
| CoAP over UDP / TFTP | CoAP distinguishes a confirmable message's ACK from the resource response. Basic TFTP advances by numbered data blocks and ACKs with retransmission on timeout. | Expose a CoAP request result or TFTP file transfer progress. A block or message acknowledgment covers its respective protocol step. [CoAP](https://datatracker.ietf.org/doc/html/rfc7252) · [TFTP](https://datatracker.ietf.org/doc/html/rfc1350) |
| RTP/RTCP · OSC over UDP | RTP sequences and timestamps media. RTCP can report reception quality. OSC sends addressed messages with arguments or bundles with time tags. | A media or control plugin can handle late frames, stale control values and loss according to their time constraints. The basic datagrams do not guarantee reliable delivery. [RTP/RTCP](https://datatracker.ietf.org/doc/html/rfc3550) · [OSC](https://opensoundcontrol.stanford.edu/spec-1_0.html) |
| KCP / ENet | KCP supplies reliable transfer through acknowledgments and retransmission. The integrator supplies underlying I/O and clock updates. ENet offers reliable and unreliable delivery modes. | Before using a session, verify duplex behavior, ordering, admission, backpressure and closure for the selected mode. The library alone does not establish the entire contract. [KCP](https://github.com/skywind3000/kcp) · [ENet](https://github.com/lsalzman/enet) |
| DTLS / QUIC stream / QUIC DATAGRAM | DTLS protects datagram confidentiality and integrity. Application data can still be lost or reordered. A bidirectional QUIC stream provides reliable ordered bytes. QUIC DATAGRAM shares connection protection and congestion control, without QUIC retransmission of lost datagrams. | Deadline-sensitive telemetry can use protected datagrams. A full rutis session can use an admitted bidirectional QUIC stream with message framing. [DTLS 1.3](https://datatracker.ietf.org/doc/html/rfc9147) · [QUIC](https://datatracker.ietf.org/doc/html/rfc9000) · [QUIC DATAGRAM](https://datatracker.ietf.org/doc/html/rfc9221) |

**Go integration and acceptance.** A collector can use `net.UDPConn` to retain each datagram and observed source address. Bound message sizes, send rate and receive queues. Choose a payload budget for the path MTU and encapsulation overhead to avoid reliance on IP fragmentation. NAT mappings can expire or change. Record the address and port as observations of the current path and verify stable device identity separately. When reliable ordered messages and session termination are required, prefer an existing transport providing those guarantees before calling `rutis/sessions.open(far)`. [Go net](https://pkg.go.dev/net#UDPConn) · [Path MTU](https://datatracker.ietf.org/doc/html/rfc8899) · [NAT mappings](https://datatracker.ietf.org/doc/html/rfc4787) · [Link plugin contract](../design/01-link-plugin-contract.en.md)

For a proposed acceptance test, use a local sensor with a boot generation and sequence number. Deliver samples `1, 3, 3, 2`, then stop transmission. A latest-state view should stay at sample 3, apply the duplicate's effect only once and use the late 2 to revise the observed gap. After timeout, show the last observation and sample age. Have two receivers in one group miss different datagrams and check that a successful send cannot establish receipt by the whole group.
