# Assessing the security, reliability and trustworthiness of a rutis link

[中文](network-assurance.md) · [Network groups and service boundaries](network-groups.en.md) · [Network stacks](network-stacks.en.md) · [Communication protocols](communication-protocols.en.md)

A sensor reports its temperature through a gateway. The gateway has a valid certificate, the cloud receives a message and the dashboard shows “online.” Three questions remain. Who may publish readings for this sensor? Which samples can be recovered after a ten-minute outage? Was the displayed value measured just now, or retained from yesterday?

| Dimension | Question | Who holds the evidence |
| --- | --- | --- |
| Security | Who may connect, read, publish or perform an operation? Where do confidentiality and integrity protection terminate? | The link row verifies its peer, the gateway or broker enforces boundary policy, and the application checks method and resource permissions. |
| Reliability | Which functions survive a slowdown, disconnect, full queue or path switch? How much is lost and how long does recovery take? | Transport endpoints observe paths and sessions. Queues report backlog and expiry. The application observes the first valid business result after recovery. |
| Trustworthiness | Who attests to which fact, through which intermediaries, and until when is that evidence valid? | A device or gateway claims an origin, a verifier checks identity, integrity and freshness, and the application confirms the outcome. |

The baseline is rutis 0.23.0. Section 1 describes existing behavior. Later sections give assessment criteria and proposed acceptance experiments.

## 1. What the implementation establishes today

- **gRPC admission.** On an mTLS-configured server, the Go endpoint checks the verified client certificate chain and configured certificate name before admitting the tunnel. The client reloads its CA, certificate and key for every reconnect. Replacing those files does not reauthenticate a live tunnel. A deployment requiring immediate withdrawal of existing access also needs a mechanism to terminate active connections. [Cloud admission](../../link/grpc/endpoint.go) · [Device reconnect](../../link/grpc/client.go)
- **Session trust.** Rutis uses the peer's self-declared Hello ID to name remote plugins. Link credentials stay with the adapter. A native node session trusts the admitted node, shares eligible services and events, and can permit requests to run plugins the local loader can resolve. Two independently administered domains sharing one business operation can terminate calls at an application gateway that explicitly exports and authorizes that operation. [Rutis node security model](https://github.com/arcships/rutis/blob/v0.23.0/docs/guide/nodes.en.md#security) · [Link plugin contract](../design/01-link-plugin-contract.en.md)
- **Recovery and resource limits.** The Go gRPC client implements backoff and a longer delay after admission refusal. The cloud endpoint supports draining on shutdown. The transport limits individual frame size. The non-Rust `sessions.open` interface in rutis 0.23 exposes no total session outbound queue limit. Frame-size and backlog tests establish different properties. [gRPC framing](../../link/grpc/session.go) · [Existing regression tests](../../link/grpc/reconnect_test.go) · [Queue limits in the contract](../design/01-link-plugin-contract.en.md)

## 2. Assess security at each hop

Trace a reading from device to broker to site gateway to cloud application. Mark each TLS termination point, who can read or change the plaintext, and where admission and operation authorization take place. A transparent relay can forward end-to-end protected data. A gateway terminating the protocol becomes another trusted party. Four questions apply along the path.

1. **Identity and permission.** The operator specifies trust anchors, expected peer identity, authorized directions and scope. Discovery records, device tags and service names can identify candidates. Connection admission still verifies the peer, and topic publication or a method call still requires authorization. Two legitimate devices in the same domain may hold different permissions. [Service identity in TLS](https://datatracker.ietf.org/doc/html/rfc9525)
2. **Data protection.** If two TLS connections terminate at the broker, the cloud can verify the broker it connected to. To require evidence that a record originated at device A and remained unchanged through a forwarder, the application can verify device-generated object integrity covering origin, data, sequence and relevant context. This requires managed verification keys. OSCORE illustrates object protection through compatible CoAP proxies on constrained devices. [TLS](https://datatracker.ietf.org/doc/html/rfc8446) · [OSCORE](https://datatracker.ietf.org/doc/html/rfc8613)
3. **Rotation, withdrawal and partition.** Establish who issues, rotates or revokes credentials, when live sessions end and when directory entries or queued requests expire. For sensitive operations, the policy owner chooses whether an isolated verifier should deny, defer or accept a time-limited cached grant. On queue recovery, check permissions and deadlines as required by the operation, including requests enqueued before revocation and delivered afterwards.
4. **Plugin and configuration trust.** A local plugin that can read device keys or change export rules is itself a trusted party. The operator verifies package origin and version, limits credentials available to each row and keeps rollback information for policy revisions. Diagnostics can retain identity references, error categories and policy versions while keeping tokens, private keys and full business payloads out of logs. [Row-level credential and management ownership](../design/01-link-plugin-contract.en.md)

## 3. Measure reliability through failure outcomes

| Failure | Infrastructure response to evaluate | Observable outcome |
| --- | --- | --- |
| A fleet disconnects together | Bound individual attempts and concurrent dials. Back off by error category. Evaluate jitter, an overall retry budget and which layer owns retries. | Attempt rate, distribution of time until usable service, and peak load on the authority or broker. [Retries and jitter](https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/) |
| A consumer slows or stalls | Bound in-flight work, queued bytes and age. Depending on the contract, block, reject, coalesce state or persist. Commands, snapshots and audit events can require different policies. | High-water mark, oldest message age, expirations and drops, and whether other tenants can still complete requests. [Overload and cascading failures](https://sre.google/sre-book/addressing-cascading-failures/) |
| A degraded direct path switches to a relay | Validate the alternate path and bound flapping. A new session has its own lifetime. The outcome of an in-flight call may be unknown. | Record path recovery, session recovery and first business success separately. Count executions associated with the same request ID. |
| A domain partitions or some members disappear | Record observation scope and validity. Distinguish last seen, unknown and explicit withdrawal. Return per-member outcomes and let the application decide whether partial results suffice. | A reachable directory with an unreachable service, partial group replies and stale records or expired commands arriving after reconnect. |
| A cloud service restarts or upgrades | Stop admitting sessions and drain or terminate live sessions within a deadline. Identify durable state and state the peer must rebuild. | Whether idle tunnels, blocked senders and outstanding calls end, and whether sessions and subscriptions recover. [gRPC plugin guide](../guide/link-plugins.en.md) |

Select indicators and objectives per deployment. For example, divide samples completed and returned before expiry by admitted sample requests. Also count admission and overload rejections so that rejecting more requests cannot disguise a loss of service. Separate path, session and application metrics by observation point. The operator sets thresholds from battery life, bandwidth, deadlines and acceptable loss.

## 4. Trustworthiness depends on attributable evidence

A temperature query might yield four facts. A link row admitted a particular gateway at a given time. A broker accepted a publication. A collector received a sample that the device timestamped at 10:01. A device application reported completion for a request ID. For each fact, identify the claimant, subject, observation point, time and scope of validity. User-facing outcomes may include unknown, expired or reported only by the gateway. [MQTT acknowledgments and recovery](communication-protocols.en.md)

- **Provenance and freshness.** Preserve device measurement time, receipt time, sequence or boot generation, and the gateways on the path where known. Label unknown clock error. A verified signature can bind content to a signer. Calibration, installation location and physical measurement accuracy require separate device or application evidence.
- **Delivery and execution.** Use a stable operation ID across enqueue, forwarding, device reply and business commit. When acknowledgment is lost, support outcome lookup or an idempotent retry under the application contract. A delivery acknowledgment establishes only what the acknowledging party can observe. [Communication protocol research](communication-protocols.en.md)
- **Evidence strength follows its use.** A trusted gateway and sample age may suffice to display the latest reading. If a decision also depends on device software state, a verifier can appraise remote attestation evidence under a policy and check freshness of the result. Attestation supports the claims covered by the evidence. The relying party still decides whether to authorize the operation. [IETF RATS architecture](https://datatracker.ietf.org/doc/html/rfc9334)

## 5. Three repeatable acceptance scenarios

| Scenario | Proposed local experiment | Outcomes to distinguish |
| --- | --- | --- |
| IoT device reporting through MQTT | Publish a retained reading with device ID, measurement time and sequence, then disconnect the device. Resubscribe the collector, withdraw the device's publish permission on the test broker, then reconnect the device with its original credentials and attempt to publish. Use a separate live test session to check when the policy takes effect. | The old sample retains its measurement time and the UI can show it as stale. Record separately whether the broker accepts a new publication, what happens to live sessions and how queued records are labeled. |
| Two administrative domains sharing a gateway | Give devices in two domains the same local name. Export only a read operation for one device. Compare an authorized read, an unauthorized write and a disconnected inter-domain path. | An audit identifies origin domain, operation, decision maker and policy version. A visible name grants no additional method access. On partition, the directory shows its last observation and age. |
| An in-flight job with two paths | Interrupt the direct path after the test application commits a job but before its receipt returns. Establish a fresh session via a relay. Query the original request ID before deciding whether the application permits a retry. | The network reports path and session recovery. The application can distinguish completed, pending and unknown and report the number of actual executions. |

These are proposed acceptance criteria. Existing gRPC admission, credential reload, draining and two-host tests provide evidence for those specific behaviors. Integration owners still need to verify cross-protocol revocation, provenance and cross-domain auditing in the deployed system.
